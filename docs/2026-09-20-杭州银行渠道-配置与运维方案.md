## 1. 管理员退款：代码现成，渠道侧零改动

### 1.1 入口与链路

运营平台的退款入口在 **`PayOrderController`**（不是 `RefundOrderController`——后者只有查询）：

| 入口 | 位置 |
| --- | --- |
| `POST /api/mgr/payOrders/refunds/{payOrderId}` | `blue-whale-pay-manager/.../ctrl/order/PayOrderController.java:154` |
| 权限点 | `ENT_PAY_ORDER_REFUND`（运营端 + 商户端均有种子，`init.sql:536` / `:640`） |
| 前端 | `bluewhalepay-ui-manager/src/api/manage.js` |

**它不直接调渠道**，而是二段链路：

```
运营平台
  │  JeepayClient(paySiteUrl, mchApp.appSecret)
  ▼
支付网关商户 API   POST /api/refund/refundOrder   (RefundOrderController.java:66)
  ▼
渠道           HccbRefundService.refund()   ← 本次已实现
```

### 1.2 前置校验（运营端已做）

- 订单必须 `STATE_SUCCESS`，否则 400「订单状态不正确」
- `refundAmount + 已退金额 ≤ 订单金额`
- `refundReason` 必填

### 1.3 对渠道接入的影响

**无需额外开发。** `HccbRefundService` 已覆盖，退款所需三要素（`origTxnOrderId`/`origRespTxnSsn`/`origRespTxnTime`）已随支付成功落库。

⚠️ 但**整条链路从未端到端验证过**，且强依赖 `paySiteUrl` 配置正确 —— 见 §2。

## 2. ⚠️ 通用配置：`paySiteUrl` 承担了互相冲突的两个职责

### 2.1 现状

`t_sys_config` 表中四个地址配置：

| key | 说明 | 种子值 |
| --- | --- | --- |
| **`paySiteUrl`** | 支付网关地址（不含结尾 `/`） | `http://127.0.0.1:9216` ⚠️ |
| `mchSiteUrl` | 商户平台网址 | — |
| `mgrSiteUrl` | 运营平台网址 | — |
| `ossPublicSiteUrl` | 公共 OSS 访问地址 | — |

### 2.2 `paySiteUrl` 是三个用途共用的一个值

| 用途 | 取值来源 | 需要的可达性 |
| --- | --- | --- |
| **① 银行异步通知地址** `backEndUrl` | `AbstractPaymentService.getNotifyUrl()` = `paySiteUrl + /api/pay/notify/hccb[/{payOrderId}]` | **银行 → 我们**：须**公网可达** |
| **② 运营平台发起退款** | `PayOrderController:186` 的 `JeepayClient(paySiteUrl, ...)` | **运营平台 → 网关**：须运营平台可达 |
| **③ 二维码图片地址** | `genScanImgUrl()` = `paySiteUrl + /api/scan/imgs/...` | 用户浏览器可达 |

### 2.3 ⚠️ 架构约束

**这三者只能用同一个值。** 若网关部署在内网、运营平台在外网，或反之，则无法同时满足 —— 系统**不支持**区分「内网网关地址」与「公网回调地址」。

**处置建议**：

| 部署形态 | 是否可行 |
| --- | --- |
| 网关直接暴露公网（运营平台、银行都走公网） | ✅ 配公网地址即可 |
| 网关在内网 + 前面有公网反代 | ✅ **必须让公网反代地址与运营平台访问地址一致**（如统一用域名） |
| 网关内网 + 运营平台内网 + 银行需公网 | ❌ **需改造**：拆分 `paySiteUrl`（内）与 `callbackSiteUrl`（外） |

> 若走第三条路，改造点：`AbstractPaymentService.getNotifyUrl()` / `AbstractRefundService.getNotifyUrl()` 改用一个新增的配置项，`DBApplicationConfig` 增加字段，`t_sys_config` 增加一行。约 20 行改动。

### 2.4 投产必配清单

- [ ] `paySiteUrl` 改为**生产网关的公网地址**（不含结尾 `/`），例如 `https://pay.example.com`
- [ ] 确认该地址从**银行侧**可达（`{paySiteUrl}/api/pay/notify/hccb` 能被外部 POST 到）
- [ ] 确认该地址从**运营平台侧**可达（`{paySiteUrl}/api/refund/refundOrder`）
- [ ] 其余三项按实际部署填写

## 4. 代码缺口

### 4.1 退款异步通知（银行 → 我们）：未实现

**现状**：`HccbRefundService` 已实测退款为**同步终态**（响应含 `settleDate`/`settleAmt`），因此当前**不需要**退款回调。

**已确认不需要实现**：实测退款响应同步返回终态（带 `settleDate` 清算日期 + `settleAmt` 清算金额），银行不另发退款通知。
`HccbRefundService` 拿到 `respCode=0000` 即置 `CONFIRM_SUCCESS`，正确。

若银行将来改为异步退款，才需补 `IChannelRefundNoticeService`。

### 4.2 关单（我们 → 银行）：未实现

**现状**：未实现 `IPayOrderCloseService`。

**影响**：本地订单超时后由 `PayOrderExpiredTask` 关闭，但**银行侧订单仍然开着**（收银台令牌 30 分钟内有效）。极端情况：用户在第 29 分钟付款成功，而本地订单已被关闭 → `updateIng2Success` 因订单非「支付中」而失败，**钱收了却记为已关闭**。

**现有缓解**：`HccbQr.preCheck` 强制订单有效期 ≥ 30 分钟（收银台令牌有效期），使「本地关单」晚于「令牌失效」，二者不重叠。

**建议**：保持现有缓解。若银行提供关单接口，可补 `IPayOrderCloseService` 做双保险。**需向银行确认是否有主动关单接口**（接口文档 2.13 关单接口用的是 `1006/100610`，属微信被扫关单，主扫是否适用未知）。

### 4.3 退款回调下游（我们 → new-api）：依赖对方

**现状**：`PayMchNotifyService.refundOrderNotify()` 会在退款成功后回调商户配置的 `notifyUrl`。

**缺口**：new-api 侧**是否已实现退款回调接口**未确认。若未实现，new-api 无法感知退款结果（本地充值记录不会回滚）。

**建议**：与 new-api 确认：① 退款回调地址；② 是否需要（充值退款是否影响用户额度）。

### 4.4 类继承待优化（次要）

`HccbRefundService` / `HccbPayOrderQueryService` 均 `extends HccbPaymentService` 以复用 `request()` / `getMchParams()`。

- 好处：零重复
- 代价：语义上退款服务继承了支付服务的 `getNotifyUrl()`（指向 `/api/pay/notify/hccb`），而退款的回调地址应是 `/api/refund/notify/hccb`（`AbstractRefundService` 提供）

当前不构成 bug（退款回调地址未被使用），但**若将来实现 4.1，需调整继承关系**：抽出公共基类，或让退款服务改为 `extends AbstractRefundService` 并复制 `request()` 逻辑。

## 7. 证书配置机制（已对齐既有渠道惯例）

### 7.1 前端上传

渠道配置表单是 JSON 渲染（`config_page_type=1`），`type: "file"` 的字段由通用组件处理：

| 环节 | 实现 |
| --- | --- |
| 表单渲染 | `bluewhalepay-ui-merchant/src/views/mchApp/MchPayConfigAddOrEdit.vue:65-78`（`item.type === 'file'`） |
| 上传组件 | `JeepayUpload.vue`，`action = upload.cert` |
| 上传端点 | `POST /api/ossFiles/cert` → `OssFileController.singleFileUpload` |
| 存储位置 | `OssSavePlaceEnum.PRIVATE`（私有目录，不允许 URL 直读） |
| 后缀限制 | `ALL_SUFFIX_FLAG = "*"` —— **允许全部后缀，`.pfx` 可上传** |
| 落库 | 返回的文件路径存入 `t_pay_interface_config.if_params` 的对应字段 |

> ⚠️ **本渠道证书密码不做脱敏**：`"star":"1"` 已移除（它会让前端编辑时清空密码框），`deSenData()` 直接回显明文。
`deSenData()` 仅被详情接口 `getByAppId`/`getByMchNo` 调用，列表接口走 `selectAllPayIfConfigListByAppId`，**不经过它**——列表不泄露密码。

### 7.2 运行时读取

与 ysfpay / wxpay 保持一致：

```java
// HccbPaymentService.request()
String certPath = channelCertConfigKitBean.getCertFilePath(cfg.getMchCertFile());
byte[] cert = HccbKit.readCertFile(certPath);
```

| 渠道 | 读取方式 |
| --- | --- |
| ysfpay | `channelCertConfigKitBean.getCertFilePath(isvParams.getIsvPrivateCertFile())` → 把路径传给 SDK |
| wxpay | `channelCertConfigKitBean.getCertFilePath(cert)` → `wxPayConfig.setKeyPath(...)` |
| **hccb** | `getCertFilePath(...)` → **读字节**（CFCA SADK 接口要 `byte[]`，非路径） |

`ChannelCertConfigKitBean` 负责本地不存在时从 OSS 私有目录下载（`ChannelCertConfigKitBean.java:30`）。

**证书不缓存**：每次请求重新读取。多商户隔离天然成立，且证书轮换（测试→生产）后立即生效。

### 7.3 字段命名

对齐既有惯例（`isvPrivateCertFile`/`isvPrivateCertPwd`、`apiClientCert`/`apiClientKey`）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `mchCertFile` | text（表单为 `file`） | 商户证书文件名（`.pfx`） |
| `mchCertPwd` | text | 商户证书密码（明文回显） |
| `bankCertId` | text | **银行**签名证书标识（信任锚），非文件 |

## 8. 各模块改动范围（是否需要动 manager / 前端）

### 8.1 结论

| 模块 | 是否需要改 | 原因 |
| --- | --- | --- |
| `blue-whale-pay-core` | ✅ 已改 | `CS` 常量、`HccbNormalMchParams`、`PayOrder` 实体 |
| `blue-whale-pay-service` | ✅ 已改 | `PayOrderService` 成功回写重载 |
| `blue-whale-pay-payment` | ✅ 已改 | 渠道实现 |
| **`blue-whale-pay-manager`** | ❌ **不用改** | 后端**零硬编码渠道引用**（grep `ysfpay/xxpay/plspay` 无命中），全部 DB 驱动 |
| **`bluewhalepay-ui-manager`** | ❌ **不用改** | 见 §8.2 |
| **`bluewhalepay-ui-merchant`** | ❌ **不用改** | 同 §8.2（另注：`PayTest.vue` 支付测试页只硬编码了 `WX_NATIVE`/`ALI_QR` 等演示入口，属**商户自助测试页**，不影响管理端配置） |

### 8.2 为什么前端不用改：`config_page_type` 分派

渠道配置表单由接口定义的 `config_page_type` 字段决定：

```js
// MchPayIfConfigList.vue:260-266
} else if (record.configPageType === 1) {
    mchPayConfigAddOrEdit.value.show(...)      // ← 通用 JSON 渲染表单
} else if (record.configPageType === 2) {
    if (record.ifCode == 'wxpay') { ... }      // ← 仅 wxpay / alipay 有自定义表单
    else if (record.ifCode == 'alipay') { ... }
}
```

`hccb` 用 `config_page_type = 1` → 走**通用表单**，前端无需新增组件。

### 8.3 通用表单的能力边界

`MchPayConfigAddOrEdit.vue` 支持 **3 种字段类型**：

| 类型 | 渲染 | schema 写法 |
| --- | --- | --- |
| `text` / `textarea` | `<a-input>`（半宽 / 全宽） | `{"name":"x","desc":"...","type":"text","verify":"required"}` |
| `radio` | `<a-radio-group>` | `{"type":"radio","values":"04,03,06","titles":"外部商户接入,杭州银行内部系统,杭州银行POS系统"}` |
| `file` | 只读输入框 + `JeepayUpload` | `{"type":"file"}` |

加 `"star":"1"` 的字段在详情接口读取时脱敏——**本渠道不使用该标记**（见 §7.1，证书密码需回显）。

**hccb 的字段全部落在这三种内**，且**字段间无联动**，因此不需要 `config_page_type=2`。

### 8.4 什么情况才需要定制化（`config_page_type=2`）

| 渠道 | 定制原因 |
| --- | --- |
| `wxpay` | 上传 `.p12` 后需**解析证书、自动回填序列号** —— 字段联动 |
| `alipay` | 「证书模式 / 密钥模式」**条件显隐** |

**hccb 无此类需求**。若将来需要在保存前校验 `.pfx` 与密码是否匹配，那时才需要定制。

### 8.5 schema 已做的优化

`aesWay`/`signMethod`/`encoding` 三个固定常量**已从表单移除**，写死在 `HccbKit`（`AES_WAY_EXTERNAL`/`SIGN_METHOD`/`ENCODING`）。
原因：前端 radio 会把 `"04"` 强制转成数字 `4`，既存不了银行要求的两位编码、编辑时又反选不上——索性不进表单。

**固定常量不进表单，写死在代码里**（`HccbKit` 常量）：

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `AES_WAY_EXTERNAL` | `04` | 接入方式（外部商户接入） |
| `SIGN_METHOD` | `01` | 签名方式 |
| `ENCODING` | `UTF-8` | 编码方式 |

> ⚠️ 为什么不放进表单：这几个值对外部商户接入是固定的，且若用 `radio` 类型，
> 前端会把数值型选项强制转成数字（`Number("04") === 4`），导致落库存成 `4` 而非银行要求的 `04`。
> 既不能存对、又会引起编辑时反选不上，故直接写死，从根上绕开。

> ⚠️ `ChannelRetMsg.channelOriginResponse` 在支付链路上**没有持久化路径**（仅分账流程消费）。原始响应排查看应用日志 `[hccb] 响应报文`。
